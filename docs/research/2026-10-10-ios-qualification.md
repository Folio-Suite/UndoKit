# iOS and iPadOS qualification requirements

Research for [Establish iOS qualification requirements](https://github.com/Folio-Suite/UndoKit/issues/4), supporting [Prepare UndoKit’s multiplatform public preview release](https://github.com/Folio-Suite/UndoKit/issues/2). Inspected on 2026-10-10 at source commit `9e5cf63b7ba89247de8cedd9308329e74c13f82a`.

## Finding

The production design has a plausible iOS path: Foundation, Core Data, CryptoKit and Darwin are its imported system modules; its public contracts are Swift, and its store and transaction owners use MainActor isolation. This is a portability inference, not a successful iOS build or runtime qualification. The release still needs explicit iOS settings, production tests on iOS, independent installation hosts, UIKit routing evidence, and device lifecycle/persistence evidence. No implementation or release-support decision is made here.

The existing accepted [Independent source package ADR](../adr/0004-independent-source-package.md) explicitly defers iOS qualification and binaries. The next platform/distribution decisions must deliberately supersede its release-scope clauses.

## Apple constraints verified

- **UIKit routing:** `UIResponder.undoManager` finds the nearest manager in the responder chain. UIKit controls can own managers; Apple specifically identifies UITextField’s manager being cleared when it resigns first responder. A host must prove that commands reach the intended router across focus/scene changes. [Apple: UIResponder undoManager](https://developer.apple.com/documentation/uikit/uiresponder/undomanager).
- **Core Data queues:** managed objects belong to their context queue; Apple's viewContext is a main-queue context. MainActor storage ownership fits that restriction, while synchronous persistence on that actor still warrants responsiveness measurement. [Apple: Using Core Data in the background](https://developer.apple.com/documentation/coredata/using-core-data-in-the-background), [viewContext](https://developer.apple.com/documentation/coredata/nspersistentcontainer/viewcontext).
- **Backgrounding:** foreground work has bounded background time. UIKit background assertions require balanced ending and an expiration handler; they neither make closure unlimited nor replace durable reconciliation. Host-managed background assertions around accepted work are a decision input, not a new framework-owned lifecycle API requirement. [Apple: Extending background execution time](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time), [beginBackgroundTask](https://developer.apple.com/documentation/uikit/uiapplication/beginbackgroundtask(expirationhandler:)).
- **Protection:** Apple documents the Core Data store default as complete-until-first-user-authentication. Production does not set `NSPersistentStoreFileProtectionKey`; that default does not establish identical protection for its Darwin-created owner file or copied files. Inspect actual attributes and locked-device behavior for every artifact, and test failure/recovery without resetting data. [Apple: NSPersistentStoreFileProtectionKey](https://developer.apple.com/documentation/coredata/nspersistentstorefileprotectionkey).
- **Placement and backup:** Application Support is appropriate for non-user-visible support data and participates in backup; caches/temporary locations are not durable equivalents. Choose how host data and history are backed up/restored together, preserving working identity. [Apple: Using the file system effectively](https://developer.apple.com/documentation/foundation/using-the-file-system-effectively).
- **Publication gap:** [HistoryStoreStorage, lines 213–216](https://github.com/Folio-Suite/UndoKit/blob/9e5cf63b7ba89247de8cedd9308329e74c13f82a/UndoKit/Modules/Storage/HistoryStoreStorage.swift#L213-L216) reads `volumeAvailableCapacityForImportantUsageKey`. Apple categorizes that as a required-reason disk-space API; the inspected tree contains no `PrivacyInfo.xcprivacy`. For SDK use, Apple's guidance requires the SDK's own applicable manifest rather than relying on the host's declaration. `E174.1` is a candidate reason for checking capacity before writes; final review must verify the full allowed-use conditions and packaging. [Apple: Required-reason APIs](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api), [API categories and reasons](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype).
- **Hardware evidence:** Apple's Simulator guidance says it must not be the sole testing platform and differs in hardware/performance. Treat locked-device protection, real suspension/termination, touch/keyboard input and representative performance as device qualification. The cited Simulator guide is archived; use it for that broad principle, not its historical hardware-feature list. [Apple: Getting started in Simulator](https://developer.apple.com/library/archive/documentation/IDEs/Conceptual/iOS_Simulator_Guide/GettingStartedwithiOSSimulator/GettingStartedwithiOSSimulator.html).

## Deployment-floor decision inputs

A read-only `xcodebuild -project UndoKit.xcodeproj -scheme UndoKit -sdk iphonesimulator -derivedDataPath /private/tmp/undokit-ios-research-derived -showBuildSettings` inspection succeeded after retrying outside sandbox restrictions. With the installed iOS Simulator 27 SDK, the framework resolves `IPHONEOS_DEPLOYMENT_TARGET = 17.0`, `SWIFT_VERSION = 6.0`, `ARCHS = arm64 x86_64`. This is a local toolchain-derived default, not a chosen support promise, archive inspection or compiled-runtime result. The initial sandbox attempt failed on Simulator/cache access, not source code.

Apple's installed iPhoneOS SDK is additional primary availability evidence: `NSPersistentContainer.h:21` marks the class iOS 10+; `NSURL.h:640` marks important-usage capacity iOS 11+; CryptoKit's `arm64e-apple-ios.swiftinterface:306–307` marks SHA256 iOS 13+. These spot checks do not establish the entire production API floor or Swift concurrency deployment floor. The exact SDK roots were `/Applications/Xcode.app/Contents/Developer/Platforms/iPhoneOS.platform/Developer/SDKs/iPhoneOS.sdk/System/Library/Frameworks/` (CoreData headers, Foundation headers, CryptoKit modules).

**Recommendation for the platform decision:** evaluate iOS/iPadOS 17 as the first qualification candidate because it matches the current effective framework setting; keep macOS 14 as the existing source baseline. Make the choice based on available oldest-runtime/device evidence and desired host coverage, not on API spot checks or SDK default values alone. Record minimum OS, SDK/producer Xcode, source/binary consumer Swift versions, device/simulator architectures, and exclusions independently. No iOS floor is settled by this note.

## Proposed qualification evidence, not yet run

1. **Build and installation:** choose explicit deployment floors; compile production package/project for device and simulator. Run all applicable production tests on iPhone and iPad simulators at the chosen floor and a current OS. Independent hosts must build source-package, project and binary routes, then open/reopen a store, record/undo/redo, and reconstruct retained state using their shipped model. Verify one dynamic runtime when both an app and its domain framework import UndoKit; inspect installed resources and any privacy manifest. Archive/device build success remains weaker than launch proof.
2. **Native host behavior:** UIKit host with UITextView and UITextField; test composed/marked text, focus resignation, provisional grouping, repeated Undo/Redo while work is pending, rejection and unknown outcomes, selection/presentation refresh, and hardware keyboard commands. On iPad, use multiple scenes/scopes and verify one window cannot redirect another's pending invocation. Touch/gesture invocation needs explicit host support and verification if promised.
3. **Durable crash boundaries:** a separate persistent host receipt/domain store plus production UndoKit; force process death at preparation, delivery, host acceptance and finalization boundaries. Relaunch without graceful close, query authoritative host outcome, and prove one semantic effect, correct suspension/availability, and preservation of unrelated scopes. A process-local fake host or historical crash prototype cannot prove that contract.
4. **Device lifecycle and protection:** physical device tests with debugger detached; background/foreground during active callbacks and closure, expiry of any host-owned background assertion, lock/unlock and post-reboot first-unlock conditions where applicable. Inspect SQLite/WAL/SHM/owner/copy protections, failed-save behavior, owner release after death, and recovery after storage becomes available. Run on representative iPhone and iPad hardware, recording OS and signing/install route; test unobservable system death through durable evidence rather than relying on termination callbacks.
5. **Retention/storage/scale:** run production retained-history, read-only, independent-copy, corruption and capacity cases on iOS; measure main-thread latency, memory and storage for representative histories on device. Choose explicit preview budgets before interpreting scale results. Validate backup/restore with corresponding host data/receipts, or document the unsupported boundary. No app-extension, cloud-sync, Catalyst, watchOS or document-provider qualification is implied.

Research performed source/docs/SDK inspection and effective-settings inspection only. No iOS build, simulator test, physical-device run, archive, privacy report or production lifecycle probe was executed. Maintainer decisions remain platform/toolchain coverage, lifecycle guidance, resource/manifest delivery, compatibility boundaries and measurable acceptance budgets; full Folio/KitchenMemory adoption stays separate.
