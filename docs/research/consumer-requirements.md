# Folio and KitchenMemory requirements for UndoKit

Research for [Inventory Folio and KitchenMemory undo requirements and integration seams](https://github.com/ctwelve/UndoKit/issues/2), a child of [Define UndoKit for Folio and KitchenMemory](https://github.com/ctwelve/UndoKit/issues/1).

Date: 2026-09-25 (America/Chicago). Status: consumer-source inventory and design inputs; no framework implementation or runtime acceptance.

## Finding

The consumers justify shared durable history infrastructure, but not one shared undo policy. Folio requires long, branching history owned by each independently saved document; KitchenMemory requires a bounded, eligible action timeline owned by a logical scene within its owner/store/Kitchen scope. Both require host-owned semantic acceptance and recoverable command identity. History persistence and native presentation must not become alternate authorities for whether an edit actually happened. These are accepted consumer requirements, not capabilities either current codebase has fully implemented. [Folio history][f-history] [KitchenMemory ADR][k-adr]

The narrow common boundary is therefore **history records and lifecycle, host-defined semantic operations and outcome evidence, plus native presentation of currently eligible history**. This is a synthesis for design discussion, not a selected protocol or API. It must support the differences below without forcing Folio to discard branches at 100 groups or making KitchenMemory undo another scene's action. [Folio history][f-history] [KitchenMemory ADR][k-adr]

### Folio preservation requirements that affect the data model

1. **Recording Off is not “no undo.”** Global default is On; document setting is Use Global/On/Off. Off preserves ordinary open-session Undo, current-work recovery, existing history, and named checkpoints. Re-enabling begins a baseline and does not claim missing edits were recorded. This separates recoverability, native actionability, durable automatic recording, and checkpoint retention. [Folio history, recording settings][f-history-settings]
2. **Omission is a coordinated successful-save transition.** Remove Existing History and Omit History are explicit author actions. Successful overwrite establishes a new baseline and clears live history in every connected editing context; failed save preserves existing history. Omission does not change subsequent effective recording preference. Current Comments, unresolved Proposed Revisions, current attribution, and required Arrangement snapshots/elaborations survive. It makes no secure-erasure promise about prior exports/backups/native Versions. [Folio history, recording settings][f-history-settings] [Arrangement history][f-arrangement-history]
3. **Old content can be current content.** An Arrangement may pin a revision without making it a named checkpoint. A retained older snapshot and its local elaborations can be required by the current Arrangement. History pruning cannot identify disposable resources by age or by “historical revision” alone. Automatic adoption of a newer source revision is an undoable action of the containing document; pinned content changes only by deliberate adoption. [Arrangement contract][f-arrangement]
4. **Atomicity includes dependencies.** Compound semantic operations succeed or fail as a whole, including effects beyond database rows. Checkpoints include owned content, unplaced material, research records and exact dependency versions; no automatic cross-document checkpoint transaction is promised. Stable request identity makes internal delivery retry return the existing outcome, while a new automation invocation is a new request. [Folio history][f-history]
5. **Archive reconstruction is distinct from replay.** Complete archival folios include applicable history and exact dependencies; omitted history is explicitly declared. Compatible independent readers must preserve unknown structured extension data and durable fallbacks. Folio does not require historical command replay to reconstruct current state. Whether UndoKit offers an export representation, or the host translates a history reader into its archive, remains open. [Archival contract][f-archive] [Semantic model][f-model] [Folio history][f-history]
6. **Editorial acceptance is not operation acceptance.** Creating/editing/accepting/rejecting Proposed Revisions is undoable. An accepted semantic edit can retain a proposal without accepting its wording. An “accepted” status in a shared API must have a precise history/domain meaning and not imply editorial approval. [Folio history, editorial material][f-history-editorial]

### KitchenMemory accepted first scope and later waves

The first integration is **saved-Recipe Folder moves and Tag add/remove**, single or atomic bulk, after recovery and native-routing proofs. New Folder/Tag creation, deletion/merge, and first Save are not included merely because they share the organization command seam. One accepted atomic batch is one app group; no-op members must not acquire a destructive inverse. [KitchenMemory ADR][k-adr] [Agreed KitchenMemory policy][k-agreed]

Later candidates preserve different meanings rather than expanding a generic “reverse object mutation” primitive:

- **Structured draft/media edits:** restore affected identities, authored precision/proposals, ordering and exact private media bytes without overwriting unrelated later text. Save freeze, replacement, discard and retirement are history barriers; live mutation can survive a failed draft-storage attempt. A byte budget and failure semantics remain prerequisites. [KitchenMemory matrix][k-matrix] [Recipe media][k-media]
- **Existing Recipe Save/Selection:** append a new Selection of the previous Revision, preserving the newer immutable Revision/media. Active drafts and competing authority heads veto automatic reversal. First Save and reconciliation Save need distinct policies. [KitchenMemory ADR][k-adr] [KitchenMemory matrix][k-matrix]
- **Disposition:** compensate only observed deletion/restoration evidence. Concurrent deletion can leave an item hidden; a pruned identity cannot be resurrected from undo bytes. Recovery into a new identity is a separate operation. [KitchenMemory matrix][k-matrix]
- **Active Session activity and possible Stop/Resume:** append new guarded Facts; do not erase old facts or mutate a Finished Session. Entry submission/withdrawal/redo identity is unsettled and existing pending-text characterizations must not become the undo contract. [KitchenMemory matrix][k-matrix] [Entry characterization tests][k-entry-tests]

Start, Finish, Continuation, organization deletion/merge, draft discard, Sample Pack requests, reset and pruning remain excluded under the accepted initial policy. The final app-wide acceptance scope is a separate KitchenMemory decision, not established by this research or by a working Move/Tag slice. [KitchenMemory ADR][k-adr]

### Swift Collections, Algorithms, and payload forms

KitchenMemory currently pins **Swift Collections 1.7.0** and **Swift Algorithms 1.2.1**; this is a checked-in dependency observation, not a newest-release recommendation. [Pins][k-pins] [Dependency inventory][k-dependencies]

| Existing use | What it establishes for UndoKit design |
| --- | --- |
| `IdentityCollection` uses `OrderedDictionary` for first-seen coalescing and `Algorithms.uniqued(on:)` for uniqueness. | Stable order and duplicate-identity semantics matter. A collection's insertion order must not silently replace host canonical command ordering/digest rules. [Source][k-identity] |
| `CausalGraph` uses `OrderedDictionary`, `OrderedSet` and `Deque`; `OrganizationEvidence` uses `Heap<Int>` to select causally ready receipts in canonical priority order. | These packages already remove real traversal/bookkeeping work, but the data structures do not select a valid inverse or define causal policy for UndoKit. [Graph][k-causal] [Evidence][k-evidence] |
| `CookingSessionOutbox` holds `Deque<PendingCookingSessionCommand>` and converts at the existing array persistence boundary. | Current consumer format compatibility is deliberate. This example does not require a new framework API to expose low-level arrays; a typed facade/codec can preserve ergonomic host types while keeping its durable representation versioned. [Source][k-outbox] |
| First-wave organization commands use typed values, arrays, sets, IDs, dates and nested enums/commands. Later drafts include authored identity/precision and private image bytes. | Existing requirements already exceed generic “set this property back.” They do not yet demonstrate a public Collections type that must be frozen into UndoKit's binary ABI. Maintain the user's requested ability to submit typed host values, including Collections where used, while separately deciding package exposure and supported codecs. [Command][k-command] [Matrix][k-matrix] [Media][k-media] [Map agreements][map] |

Preserving a Swift value's useful type at the API boundary, preserving its semantic data durably, and exposing a third-party generic type in the XCFramework interface are three different design questions. The source inventory supports investigating all three; it does not justify requiring callers to manually decompose every value into Foundation objects or persisting arbitrary runtime object graphs. The idiomatic Swift and independently usable Objective-C interfaces are explicit map agreements. [Map agreements][map]

External-resource handling also needs an explicit host contract. KitchenMemory media distinguishes a content-addressed logical reference from optional local bytes; authority digests exclude availability-dependent bytes, and newer revisions do not erase older payloads. Folio can reference external versioned dependencies, while archival export and Editions require exact retained inputs. UndoKit must know enough about host resource reachability to avoid dropping needed inverse/checkpoint data, without claiming authority over consumer media or archive policy. This last sentence is a design inference from those retention requirements. [Recipe media][k-media] [Arrangement contract][f-arrangement] [Archival contract][f-archive]

## Tensions, unanswered questions, and focused follow-ups

No adopted contract was found requiring the same policy to behave oppositely. The following are actual design gaps or differences to preserve:

1. **What is the minimum recoverable host-operation contract?** Both consumers require stable identity and authoritative outcomes, but Folio's current Work surface has no durable receipt API and KitchenMemory's public organization repository has only throwing acceptance. Decide what can be queried without reapplying a command, how an unknown outcome blocks use, how long recovery evidence must outlive history retention, and how exact retries interact with conditional validation. [Work interface][f-work] [Repository interface][k-repository] [Accepted ownership][k-adr]
2. **Where is “accepted text edit” captured?** Folio must merge durable semantic order with its existing shared native text manager; KitchenMemory must preserve transient native text priority alongside durable app history. Determine the adapters' capture/commit point and reconstruction strategy without serializing callbacks, duplicating groups, or silently dropping text identity. [Folio editor][f-editor] [KitchenMemory native text][k-native-text] [Consumer history contracts][f-history] [KitchenMemory flow][k-flow]
3. **Which persistent identities identify history scopes?** KitchenMemory needs the same logical scene through forced termination but a new scope after explicit disposal/owner/store change. Folio needs independent document identity and coherent save/copy/restore behavior; copying a package must not accidentally link two active histories. Source identities, copy identity, restoration association and live connection identity are separate concepts. The exact copy/scene identifiers remain open. [Work Session][f-session] [KitchenMemory flow][k-flow]
4. **How are branches, checkpoints, resource references and actionability related?** Folio needs recoverable abandoned states and exact pinned dependencies; KitchenMemory needs a 100-group action limit. Decide the smallest model supporting these capabilities, and what quantitative Folio history/asset workloads will count as acceptance. “Very large” currently has no numeric target. [Folio history][f-history] [Arrangement contract][f-arrangement] [Agreed KitchenMemory policy][k-agreed]
5. **What happens when history cannot be opened or invalidated durably?** Accepted KitchenMemory policy requires preventing resurrection even if writing invalidation fails. Both consumers preserve recoverable evidence; whether safe domain editing can continue with unavailable history, and how failure markers/recovery evidence establish that safety, is unresolved. Folio's recording Off option is not an automatic authorization to downgrade on error. [KitchenMemory ADR][k-adr] [Storage research][k-storage] [Folio settings][f-history-settings]
6. **What is the package/export boundary?** Folio's current single-file reader rejects an added history store. Decide a versioned host package composition protocol and coherent snapshot/replace boundary, including restoration that preserves displaced history. Decide separately whether an archival folio carries the native database, an exported history representation, or both; Folio's independent reconstruction contract does not select this. [Work store][f-store] [Archival contract][f-archive]
7. **Which Swift and Objective-C payload/compatibility contracts earn a proof?** Test actual Codable command values and representative Collections values alongside an Objective-C immutable text snapshot. Decide codec identity/version, unavailable codec behavior, archived semantic compatibility and binary/package exposure. Current Foundation headers do not promise automatic object serialization. [Commands][k-command] [Foundation model][f-text] [Map agreements][map]
8. **How much interference invalidates which scope?** KitchenMemory's conservative policy is accepted; the complete organization-evidence fingerprint and one evolving timeline token are proposals. Specify successive undo, own accepted refresh, unrelated Save, compaction, other-scene changes and late remote evidence without transferring this invalidation policy to Folio's shared document order. [KitchenMemory flow][k-flow]

The old originating-context Folio rule and Work-owned Arrangement assumptions are explicitly superseded, so they are not alternatives to carry into the new design. Likewise KitchenMemory's earlier memory-only lifetime is superseded by ADR 0022. Exact implementation-ticket drafts and fingerprints remain proposals despite appearing in an agreed-policy research file. [Folio ADR][f-adr] [Folio history][f-history] [KitchenMemory ADR][k-adr] [KitchenMemory policy][k-policy]

## Acceptance examples to preserve in subsequent design proofs

These are required examples or directly derived test candidates, not test results. Their sources are attached so later tickets can choose concrete prototypes and lower-level fixtures.

| Example | Observable result to require |
| --- | --- |
| Folio: type in Content Unit A, rename B, undo twice, close/reopen, redo | Correct document order, stable text/paragraph/unit identities and restored actionable position. Existing cross-unit reveal behavior is a host choice to preserve or explicitly revisit. [History][f-history] [Editor tests][f-tests] |
| Folio: undo B, author C; later recover material from B | Ordinary redo follows the current path; B remains reachable in history. Recovering selected material is a new undoable edit with provenance. [History][f-history] |
| Folio: restore a checkpoint/native Version while another app is connected | Every connected view reaches the coherent restored state; displaced accepted work remains in a branch and restoration origin is recorded. [History][f-history] [Work Session][f-session] |
| Folio: recording Off, named checkpoint, then On | Open-session Undo and current-work recovery remain available; checkpoint exists; new baseline discloses unrecorded interval. [Settings][f-history-settings] |
| Folio: successful versus failed Omit History overwrite | Success clears all live contexts and historic records but retains current editorial material and required older Arrangement snapshots; failure preserves prior history. [Settings][f-history-settings] [Arrangement history][f-arrangement-history] |
| Folio: coordinated package snapshot with a prepared/accepted command and external assets | Reopen has a coherent domain/history generation and required resource versions; incomplete staging cannot replace the usable original. Exact protocol and runtime proof remain open. [Work Session][f-session] [Storage proof list][k-storage] |
| KitchenMemory: R and S move from different folders to H, undo/redo | One atomic group; each returns to its own prior folder. Each accepted compensation has a fresh identity; retry keeps the exact pending identity. [Paper exercises][k-examples] |
| KitchenMemory: add T to R (already tagged) and S (untagged), then undo | Existing R membership survives; only changed assignments are compensated. A later remote assignment is not silently absorbed into the inverse's observed set. [Paper exercises][k-examples] |
| KitchenMemory: perform two moves, undo twice | Each accepted compensation updates eligibility for the next older action. An immutable original post-state token must not falsely block the second undo. [Paper exercises][k-examples] |
| KitchenMemory: interruption before/after acceptance and finalization | Same logical scene reconciles the exact outcome and group/cursor once, without reapplying accepted content. New unrelated scene receives no inherited history. [ADR][k-adr] [Paper exercises][k-examples] |
| KitchenMemory: inverse fails, invalidation write fails, then terminate/relaunch | Exact pending compensation remains governed by existing retry; old timeline never becomes actionable merely because its on-disk invalidation failed. No false redo. [ADR][k-adr] |
| KitchenMemory: text editor teardown or navigation veto after accepted app action | Text cleanup cannot erase app history; accepted app operation/history remains accepted even if navigation is vetoed, and no automatic navigation occurs. [Native flow][k-flow] [Paper exercises][k-examples] |
| Either consumer: unsupported payload/schema or unavailable required resource | Preserve source evidence and distinguish unavailable history from empty history; eligibility and recovery behavior must be explicit before use. Current schema compatibility alone does not establish semantic payload compatibility. [Accepted recovery boundary][k-adr] [Folio semantic model][f-model] |
